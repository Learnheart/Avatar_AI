1. Objectives

Target. A kiosk avatar that notices a person standing in front of it, listens to what they say, and answers back in a natural Vietnamese voice, while an on-screen 3D avatar moves its head slowly, as someone waiting would, and moves its mouth in time with the spoken audio. It answers as a personal work assistant, from its own general knowledge and from documents the user has uploaded.

Inputs.

  • Live camera feed: is a person there, and where is their head.
  • Live microphone audio: what the person says.
  • Documents uploaded in the browser (text, Markdown, CSV, PDF, Word): the internal knowledge the avatar may answer from.
  • What a known person types on the profile page to describe themselves, and what they import there for the same purpose: a file (text, Markdown, CSV, PDF, Word) or a pasted text.
  • Who the person is: an email address and a password, with the code sent to that address when the account is created, or a Google or Facebook account, given on the page to sign in; and what they say about themselves in conversation.

Outputs.

  • A spoken Vietnamese answer played through the speaker, starting on the first sentence rather than after the whole answer is ready.
  • A 3D avatar whose head moves slowly on its own, tilts while it thinks, and whose mouth follows the audio.
  • For the operator: a step-by-step record of every turn (what was heard, looked up, answered, and how long each step took).

Scope by milestone.

Milestone Status What it delivers
MVP 1 Built, demo-ready One complete spoken turn end to end (presence → listen → understand → answer → speak), interruption by speaking over the avatar, answers from uploaded documents, a backup provider per cloud step, turn tracing
MVP 2 Built: sign-in, the short-term part, the application database, the users, the memory of typed and imported facts with its profile page, the object store, and the facts gathered from conversations with their approval Memory: the avatar follows the conversation in progress and remembers a signed-in person across visits; a profile page where the person corrects what is remembered; an application database for users; a personality for the avatar, set by the person on the same page (built)
Later Not planned Company single sign-on and sign-in approved on one's own phone, several people talking at the same time, recognising a person by face or voice, tool/function calling, accurate mouth shapes, body gestures and emotion

Constraints.

  • Latency SLA: end-to-end answer under 10s; internal target first audio under ~3.5s (the number the user actually feels).
  • Language: Vietnamese voice quality is a first-class requirement.
  • Hardware (cross-device): one codebase for an Apple Silicon MacBook (the development machine) and a Windows PC + NVIDIA RTX (not set up yet).
  • Network: must work on a restricted company network where some cloud providers are blocked — every cloud step can be pointed at another provider by configuration.
  • A turn never dies because an optional part failed. Knowledge lookup, memory, the camera and a primary provider can each fail without stopping the answer.
  • Privacy: recordings of faces and voices are off by default; a guest is never remembered.
  • Architecture principle: each capability is a cleanly bounded module that could become its own service later; the product ships as a modular monolith, not a distributed system.

3. Architecture

Three capability blocks on a stable spine. Perception feeds the Orchestrator, which drives the Conversation engine, whose output flows to Expression in the browser. Three features sit beside the turn and are consulted by it: the knowledge base, memory (typed and imported facts, and facts gathered from conversations as proposals) and the persona (the personality a person gives the avatar). Every model the system calls sits behind a fixed boundary and is chosen by configuration.

3.1 System overview

3.2 The turn, as the Orchestrator sees it

Only the Orchestrator changes this state; every other module returns values or events.

The conversation. Around the turns the Orchestrator also owns the conversation: the session of one person (a signed-in user, or a guest), which is the unit of short-term memory.

  • It opens at the first utterance when none is open.
  • Each turn that ends is recorded in it, however it ended (completed, interrupted, failed, timed out), as long as something was understood: the text heard, and the sentences of the answer that had started to play. The apology spoken when the LLM fails and a sentence that got no audio are left out.
  • Each new utterance is handed to the Conversation engine with the earlier turns; the engine itself keeps nothing between turns.
  • It closes when no face was seen for a while (only while the camera works), when nobody spoke for a longer while, when another user connects, or when the person presses "Cuộc trò chuyện mới". Only that last one may arrive during a turn: the answer is then cut as by an interruption. A page reload by the same person does not close it.

The WebSocket carries three messages for it, beside the audio, speech and state ones:

Direction Message Meaning
browser → backend conversation_reset The person asks for a new conversation
backend → browser conversation (an id, or none) A conversation opened, or the open one closed; also sent right after connecting, with the conversation still open if there is one
backend → browser transcript (the text) What the avatar heard for this turn; not sent when nothing was understood

What the avatar answers needs no message of its own: each sentence already travels with its speech.

Two more messages say whose connection it is built:

Direction Message Meaning
browser → backend auth (the session of the page, or none) Who the page is: the first message of a page, and sent again when the person signs in or out. A page that sends none is a guest's
backend → browser session (the user, or none) Whether the connection is a signed-in user's or a guest's: the answer to every auth, and sent unasked when the backend ends the session

A change of user on an open connection closes the conversation in progress.

3.3 Model backends: one contract, many providers

Each step that calls a model depends on a contract ("audio in → text out", "text in → streamed answer out"), never on a provider. Which provider answers is configuration.

3.4 Memory beside the turn MVP 2 · built

Built so far: the Orchestrator's conversation and the earlier turns given to the Conversation engine (§3.2); the application database and the users; the Memory holding the facts a person types on the profile page, and the person's active facts given to the Conversation engine with each turn; import — a file or a pasted text is kept unchanged in the object store, and one request to the language model, made outside any turn, reads it into facts that are used at once; gathering — the Orchestrator hands the Memory each turn of a signed-in person as it ends and tells it when the conversation closes, without waiting for it, and one request to the language model, again outside any turn, reads the closed conversation into proposed facts that the person approves or rejects on the profile page. Sign-in decides whose memory this is: the page presents the session it was given, on its requests and on the connection the conversation runs on, and a person who presents none is a guest.

Also built, beside the memory: the persona. A signed-in person gives the avatar a personality as a few named settings, typed on the profile page or read from a description they paste by one request to the language model, outside any turn; what is read only fills the page, and nothing is kept until the person saves. The saved settings are given to the Conversation engine with each turn of that person.

3.5 Why these boundaries

  • Capability, not model. Blocks are drawn by what they do (perceive / converse / express), so the choice of model lives inside a block and can change without reshaping the system.
  • Swappable Conversation engine. Understand → look up → think → speak sits behind one boundary with a single contract — "audio in, text + audio out." A unified realtime model could replace the whole box later; the Orchestrator and Expression don't care.
  • One owner of the turn. Only the Orchestrator knows whether the avatar is idle, listening, thinking or speaking. That is what makes interruption safe: there is one place that cancels an answer.
  • Providers are configuration. A provider being blocked, slow or replaced is solved by a setting, and a backup can stand behind any cloud step. This is what lets the same build run on an open network and on a restricted company network.
  • Optional parts stand beside the turn. The knowledge base, memory and the persona are asked for help and given a short time to answer; if they are empty, slow or failing, the avatar answers without them.
  • Lip-sync lives in the frontend, bound to the audio actually playing. Mouth movement is derived from the loudness of the audio coming out of the speaker, not from when a network packet arrived — so it stays in sync regardless of network jitter or buffering.
  • Perception is a parallel plane. Head tracking runs continuously and independently of the listen→answer turn; it is not on the critical path to speech.
  • Every step is observable. Each stage of a turn records what it received, what it produced and how long it took, so a slow or wrong answer can be traced to one step.
  • Two memories, two lifetimes. Short-term (built) is the conversation in progress: it lets a follow-up question make sense, and it disappears when the conversation ends. Long-term (built) is a small profile of one signed-in person that survives across visits.
  • A conversation is defined by the person, not by the connection. It starts when someone speaks and ends when they have walked away, stayed silent long enough, or asked for a new one. A page reload does not end it. The Orchestrator owns this boundary.
  • The history holds what was heard, not what was generated. An answer cut by an interruption is remembered up to the sentence that had started to play, so the next answer does not build on words the person never heard.
  • Identity comes from sign-in, and guests leave no trace built. Long-term memory is keyed by the signed-in user, and one user never reads another's. A guest gets the short-term memory only. Being a guest is the default and never an error: a session that is missing, unknown or over simply means a guest.
  • A session is kept on the server and can be ended at once built. The page holds a random token and the system holds only its fingerprint, so the session can be ended the moment it should be (sign-out, expiry, the person leaving) and a copy of the database signs nobody in. On a shared kiosk a kept session means the next person is taken for the previous one until it expires: its two time limits, and the option to end it when the person walks away, are the controls for that.
  • Only the wiring knows about sessions built. The Orchestrator is told a user or a guest and nothing more; signing in or out on an open connection starts a new conversation, so nothing a guest said follows the user who signs in afterwards.
  • An external account only says who the person is built. Google and Facebook are asked once for the person's identity and nothing of theirs is kept. An identity is linked to an account by a signed-in person, or by itself where the address was proved on both sides: here by a code, there by a provider that says it verified it.
  • An account proves its email built. The account is created only when the code sent to the address comes back, so nobody holds an account in someone else's name and one address has one account. Sending is a setting: a real mail server in a deployment, the backend's own log on a machine that has none.
  • Three ways into long-term memory, with different trust built. What a person types, and what is extracted from a description they import, is used at once. What the avatar heard in a conversation is only a proposal until the person approves it, or says it again on a later visit — because speech recognition mishears, and a wrong fact would otherwise stay wrong forever.
  • The profile page is the correction point built. Everything the avatar remembers is visible and editable there, and what the page shows is exactly what the language model is given.
  • The avatar's personality is a setting of the person, not of the kiosk built. It is a few named, optional settings rather than one free text, so each can be shown, corrected and limited on its own; the default character is the same settings with default values, so a setting left empty falls back to its default. Where the person asked to be addressed in a certain way in their own facts, that wins over the personality. A pasted description is only read into the settings: the person sees and saves them, and the description itself is not kept.
  • Imported originals are the source of truth built. The file a person imports is kept unchanged in one object store shared by all users; the remembered facts point back to it, and its text is re-derived from it rather than stored twice. An import that cannot be read into facts is not kept at all. The person can download the original again, and delete an import with or without the facts read from it.

4. Dataflow

4.1 One complete turn

Vision is not in this sequence on purpose: head tracking runs all the time, beside it.

4.2 The response branch (text → voice → avatar motion)

The flow that carries the sync and latency requirements.

  • Streaming, not wait-for-whole. Speech starts on the first sentence the LLM produces, so the person hears a reply around the first-audio target (~3.5s) instead of waiting for the full answer.
  • Amplitude-driven lip-sync. The mouth opens in proportion to how loud the audio is. Simple and cheap; it does not form exact vowel shapes.
  • Dead-air is the real risk, not raw latency. Because the SLA (10s) is generous, the design priority is covering the 2–4s "thinking" gap rather than shaving milliseconds.

4.3 Knowledge: from an uploaded file to an answer

  • Changing the embedding model re-indexes the stored text at the next start; nobody has to upload again.
  • No match, a slow lookup or a failure → the question goes to the LLM alone.

4.4 Memory: how a spoken fact becomes (or does not become) a memory built

  • Hearing is not remembering. A fact reaches the answers only after a human approval or a repetition; a single misheard sentence cannot. A name or a way of addressing needs the approval however often it is heard: speech recognition mishears a name the same way every time.
  • A rejected proposal stays rejected. It is kept, unused and unseen, so that the same fact is not proposed again after the next conversation. The same holds for a gathered fact the person deletes later.
  • A conversation never overwrites what is already remembered. A contradiction becomes a proposal to replace, decided by the person.
  • Recordings of the conversation are not kept. Once the proposals are made, the stored turns are deleted; only the short quote behind each fact remains. A conversation that could not be read (the language model failed, the system was stopped) keeps its turns and is read at the next start, and turns older than a set number of days are deleted either way.
  • Memory never costs the turn. Reading the profile is instant; saving turns and extracting facts happen after the audio has been sent.

4.5 When something fails

What fails What the person experiences What the system does
Speech-to-text No answer to that sentence The turn ends with an error and the avatar returns to idle, ready for the next sentence
LLM A short spoken apology A fixed fallback sentence is spoken instead of silence
Speech synthesis, for one sentence That sentence is silent The sentence is still sent as text; the rest of the answer continues
A primary cloud provider A slightly slower answer, once The backup takes over and the primary is skipped for a cool-down period
Knowledge lookup (empty, slow, failing) A general answer The question is answered without the documents
Memory (empty, slow, failing) An answer that does not know them The turn runs without the profile
Persona (none set, slow, failing) An answer in the default character The turn runs without the personality
Sign-in (the session is unknown, over, or the database fails while it is checked) The avatar answers them as a guest The connection is kept; the page is told it is a guest's
The mail carrying the code of a new account cannot be sent A message on the page, no account Nothing is kept waiting; the person can ask again
An external sign-in provider (unreachable, refuses) A message on the page, still a guest Nothing is created; the other ways to sign in are unaffected
Application database, at startup The avatar does not start Startup stops with the reason: nothing runs on a database it cannot open
Camera The avatar looks straight ahead The head returns to neutral; the camera is retried; listening and answering are unaffected
The person speaks over the avatar The avatar stops and listens The running answer is cancelled and a new turn starts
The browser connection A pause, then reconnection The running turn is cancelled; the browser reconnects by itself
A turn that takes too long An error instead of a late answer The turn is cut at a fixed limit

5. Deployment

Today: one machine, run locally. The development MacBook runs both the backend process and the browser. Windows + RTX and container packaging are not set up yet.

What runs where.

Part Where Notes
Avatar rendering, microphone capture, audio playback, lip-sync Browser Needs microphone permission and one click before audio can play
Camera reading, presence and head tracking Backend process The camera is attached to the machine running the backend
Voice detection, speech synthesis Backend process, on CPU No GPU needed; the speech model is downloaded once at first start
Speech-to-text, LLM Cloud The two calls that dominate latency
Knowledge base, embeddings Backend process + local file Embeddings may be local or a cloud call, by configuration
Users, sessions, memory, persona Backend process + the application database (a local file) Reading and proposing facts are extra LLM calls made outside the turn
Imported originals Backend process + a local folder One folder for all users; replaceable by a cloud bucket
Sign-in with an email and a password Backend process, and a mail server when one is configured Passwords are stored hashed. The code that proves an address is sent by the configured mail server; without one it is written to the backend's log and nothing leaves the machine
Sign-in with Google / Facebook Cloud, optional Off unless configured. The system must be registered at the provider under an address the provider can send the browser back to. Built, not yet run against the real providers
Tracing Backend process Sent out only when a trace backend is configured

Cross-device. The application code is the same on Apple Silicon and on Windows + NVIDIA. Since speech-to-text moved to the cloud, nothing in the turn depends on a GPU today; the Device Capability Router is kept for the day a self-hosted speech model is added, and the Windows path still has to be installed and verified on its own hardware.

Restricted networks. On the company network Groq, the speech-model download site and the frontend package registry are blocked. The system runs there by pointing speech-to-text, the LLM and the embedding at the Databricks gateway, which is reachable. The speech model must already be on the machine.

Known gaps (measured, not assumed).

  • On the Databricks path, first audio was measured at about 5 s and the whole turn at about 7–10 s: the first-audio target (~3.5s) is not met there, mostly because speech-to-text alone takes about 2 s. The Groq path could not be measured from the company network.
  • The avatar file is supplied per machine; without it the page runs with audio only.

Path to a multi-user deployment (planned, cheapest step first).

Step Database Files When it is needed
1 Local SQLite file Local folder One kiosk, or a few people taking turns
2 PostgreSQL on the same machine Local folder Several writers at the same time
3 Managed PostgreSQL Cloud bucket More than one backend instance

Each step is a configuration change for the features that store data. Two things do not follow from the database choice and need their own work before many people can use the system at once: the backend serves a single connection, and it reads a camera attached to its own machine.

Microservice / multi-machine path (not planned). Each capability block already has a clean boundary. To scale out later, a block's boundary is exposed over the network and the block moves to its own service — without redrawing the architecture above.
